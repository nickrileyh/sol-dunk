# SOL DUNK

A Flappy Dunk-style skill betting game paid in SOL. Tap to flap a winged basketball down through rings; swishes pay more than rim hits, swish streaks pay more each time, and every 6th (green) ring is a checkpoint where the player cashes out or keeps going.

## This repository is the source of truth

Several chats work on this game. Start every session from a fresh clone of `nickrileyh/sol-dunk`, and commit and push when you finish, so the next chat builds on your work instead of an older copy.

The playable demo is a claude.ai artifact, slug `fb718710-5b6b-4ad8-bf8e-4d9cee1b68b6`; publish `dist/index.html` there. Before publishing, check that its live version is the one you started from. If another session published since, split that build with `python3 tools/split_build.py <file> <dir>`, merge its changes into `src/`, and push them here. Never publish over someone else's work.

## Keeping every copy in sync

The game lives in four places, and they should always hold the same build:

1. `src/` on `main`, the source of truth.
2. `dist/index.html`, `dist/index.server.html` and the root `index.html`. `npm run build` writes all three. GitHub Pages serves the root `index.html` at https://nickrileyh.github.io/sol-dunk/ and updates a minute or two after each push.
3. The claude.ai demo artifact, published from `dist/index.html`.
4. The "Live version" line in the claude.ai project doc `claude/sol-dunk-design.md`, which gives the artifact version and the repo commit it was built from.

Finish every change in this order:

1. `git fetch` and rebase onto `origin/main`, since another chat may have pushed.
2. Call `get_artifact` on the demo. If its version isn't the one you started from, `read_artifact` it and run `npm run check -- <the file it saved to>`. If the check says the repo doesn't have that build, split it with `tools/split_build.py`, merge it into `src/` and push that first.
3. `npm run build`, then the checks under Rules.
4. Commit `src/` and the three builds together, and push.
5. Publish `dist/index.html` to the artifact.
6. Update the doc's "Live version" line with the new artifact version and commit.
7. `read_artifact` again and run `npm run check -- <that file>`. It should end with "everything is in sync".

`npm run check` on its own checks that the three builds match `src/` and that nothing is uncommitted or unpushed. Given a saved copy of the demo, it also says whether the demo is this commit's build, an older commit's (publish) or a build the repo doesn't have (merge it).

Never publish a build you haven't pushed, and don't push a game change without publishing it, so the demo and GitHub Pages always match.

## Layout

- `src/engine.cjs`: deterministic 120 Hz physics, level generation, replay and payout helpers. The client, simulator and server share it.
- `src/paytable.cjs`: generated by `sim/calibrate.cjs`. Never edit it by hand.
- `src/bot.cjs`: the human-like autopilot used by the simulator and the lobby demo.
- `src/pots.cjs`: the daily pot, a game of its own (the day's theme and course, standings by rings then score, the top three's shares, ties, rake, rollover), shared by the client, the server and the demo pot.
- `src/missions.cjs`: daily and weekly missions in rounds of three (UTC windows, targets, XP, SOL rewards, the play that unlocks each round, progress from verified levels), shared by the client, the server and the demo.
- `src/levels.cjs`: the level curve and level-up rakeback (what each kind of bet sets aside, release on a level up, claim), shared by the client and the server.
- `src/trophies.cjs`: the fifteen trophies (what earns each from a run's verified levels, their XP and SOL rewards, and the rule for claiming the SOL), shared by the client, the server and the demo.
- `src/duel.cjs`: duels (the course both players fly, how a flight is scored and compared, the pot after the house's cut), shared by the client, the server and the tests. Its course builder also builds the daily pot's course, with the day's features on top (`feat`); a duel has none, and its rings must stay exactly as they are.
- `src/special.cjs`: the special levels (twists, the generator, the day's three, each player's level in each special and the course set for a level; curves written by `sim/special.cjs`), shared by the client, the server and the simulator.
- `src/game.js`, `src/index.html`, `src/style.css`: the browser client.
- `src/fonts/`: the display font SD Display (Saira, subset to its widest width) and Archivo's × sign, with their OFL licence. `build.cjs` inlines them as data URIs and `tools/split_build.py` turns them back into files.
- `build.cjs`: inlines everything into `dist/index.html` (demo) and, with `SERVER_URL=/`, `dist/index.server.html` (real SOL). It refuses to build if `src/style.css` has unbalanced braces: an unclosed block doesn't break the page, it quietly swallows every rule after it (a lost `}` in a merge once left the depth styles inside a mouse-only `@media`, so phones never got them). After a merge that touches the end of `style.css`, look at a phone-sized screenshot too, not only a desktop one.
- `sim/`: Monte Carlo runner and calibrator (`sim/same.cjs` tells whether a change left the game playing tap for tap the same); `sim/special.cjs` measures the special courses and checks how players' levels settle, and `sim/pots.cjs` measures how far each bot gets on the pot's themed courses. `server/`: the game server (next line). `tools/`: Playwright browser checks.
- `server/server.mjs` holds the routes; `server/lib/` has `config.mjs` (every setting, and the checks that refuse an unsafe mainnet start), `db.mjs` (Postgres: one transaction per request, a ledger line for every balance change), `chain.mjs` and `payments.mjs` (deposits, withdrawals, sweeps), `botcheck.mjs`, `http.mjs` (headers, rate limits, country blocking) and `admin.mjs` (the operator API). `server/scripts/` has the admin CLI, `keygen` and the live `e2e` check; `deploy/` the Docker setup; `docs/LAUNCH.md` the launch steps; `server/SECURITY.md` the threat model.

## Rules

- **Physics changes need new payouts.** Any change to `src/engine.cjs` (physics, level settings) means bumping `VERSION`, then running `node sim/run.cjs` (about 6 minutes; `node sim/run.cjs 1 <tier> merge` re-runs one mode). After that, run `node sim/calibrate.cjs patterns.json --mode edge --write` (`npm run calibrate`). Wait for "wrote sim/out/patterns.json" before calibrating. Then re-measure the special courses with `npm run special` (about 15 minutes on two cores, with twelve twists on ten grades; `node sim/special.cjs 2000 --refit --write` re-fits the saved curves without playing); also after any change to the bot or a twist in `src/special.cjs`. Never edit its `TABLES` block by hand. Then re-measure the pot's courses with `node sim/pots.cjs`. A change that can't touch regular levels (engine v16's walls, which only special courses carry) still bumps `VERSION`; `node sim/same.cjs` in the old and the new checkout prints a digest of every tap and outcome, and when it's the same the paytable and the other twists' curves still hold (engine v17's upright and breathing rings were checked this way against v16, as was the duel's course) (`node sim/special.cjs 2000 --only=<twists> --write` measures just the new or changed twists).
- **House edge (mode `edge`):** the house keeps an edge at every checkpoint against average and good players. An average player gets back at most 90% at checkpoint 1 and loses at least 10% on every later level; a good player gets back at most 99% at checkpoint 1 and 97% from checkpoint 2 on. Pros aren't capped by default: they clear the easy levels so reliably that capping them (`--cap-pro 0.99 --cap1-pro 1.01`) shrinks the top prizes to a few × on Easy. Check the "RTP by skill" and "Best possible win" tables in the calibration output; the lobby shows each tier's real best possible win.
- **Daily pot:** a game of its own (the owner asked for it to stop riding on regular runs): one course a UTC day, the same for everyone, from a seed fixed when the pot opens and shown to all. Each attempt costs the entry and all of it goes into the pot; a player's best attempt counts, ranked by rings, then score; the best three split it (`POTS.PLACES`, half, three tenths and a fifth), ties sharing their places, and with fewer than three players the places filled share it all. The house's only edge is `POTS.RAKE` (10%) of every entry; never let it take a side. Attempts are judged only from the server's replay of the taps on the day's course (`DU.fly`), never from the client's word, and a flight that comes in after its pot has closed doesn't count (no new attempt in the last `POTS.CUTOFF_MS`). Money in open pots counts as owed. The course is the duel's escalating course with the day's theme on top (upright rings, breathing rings, every ring moving); after changing a theme, the course, the bot or the engine, `node sim/pots.cjs` should still show novices at a handful of rings, average players around ten, pros in the twenties and perfect play not always finishing, so attempts spread out and rank. A pot from before (a challenge, `goal`) refunds its entries when it closes. In the demo the other players are the autopilot, flown on the day's course, and labelled so; the leader's best flight (or your own, if you lead) flies beside you as a ghost.
- **Special levels:** three a day at 2×, 3× and 5× a fixed entry. Each course is set for the player's level in that special, and levels move like a weighted staircase: up `SP.up(x)` after a clear, down `SP.DOWN` after a miss, with up / down = (1 - p) / p for p = 90% ÷ the prize, so a level settles where the player clears p of their attempts and everyone gets back about 90% over time however they play, missing on purpose included. Keep that ratio whenever a step or a prize changes. The specials open only once a player has bet `SP.UNLOCK` entries in regular runs (0.5 SOL; `SPECIAL_UNLOCK_LAMPORTS` on the server). A level starts at `SP.START`, raised (never lowered) by the middle of the player's verified regular-run rating or their level in another special: anything that could lower a start could be faked, and a start that's too high only costs the player a few misses. Courses only have to get harder as the level rises; step 5 of `sim/special.cjs` plays new players through 40 attempts and should show every skill at about 90% from the 16th attempt on, and players who miss on purpose doing no better than honest ones. Players past the top of the scale keep winning, so accounts the server flags for beating the house can't enter. Every twist needs a course hard enough for a pro: after adding or changing a twist or a grade, the "expected return of the course set for levels 3 / 4 / 4.5" table in `sim/special.cjs` must stay at about 90% or less at level 4 for every twist and prize (the two grades past Hard level 8 exist for that: without them a pro cleared the hardest Needle course 45% of the time, 238% at 5×); `--twists=a,b,c` picks the twists steps 4 and 5 play. A twist may only depend on a ring's place in the course, never on its length, and existing twists must keep generating the same rings (their tables were measured on them). Special rings never count toward missions; entries count as play for mission SOL. Three twists use engine v17's new rings (`fx` in the recipe: Side doors, Switchback, Heartbeat); like the wall courses they take turns opening one prize a day, so the twelve ring twists' rotation is unchanged. Upright rings are `GATE_W` wider than flat ones, narrowing by `GATE_TAPER` a grade, so pros run out of easy courses; the bot flies them as gates (`decideGate` in `src/bot.cjs`). Each prize has `SP.PER_SLOT` (5) specials a day in an order that's the same for everyone (`SP.queuesFor`): a player is on the one after those they've cleared today, and after the last that prize is done until tomorrow; the server picks the twist from the day's wins it holds, never from the client. A level belongs to the prize, not the twist. Walls (three twists, `ob` in the recipe): a wall's height comes from what a ball can climb to after the ring before and drop from into the ring after (`walls()` in `src/special.cjs`); keep perfect play at about 100% on any new layout before measuring it.
- **Mission SOL:** every run counts toward daily and weekly missions whatever the bet. Missions come in three rounds a window; a round's SOL is released only once the player has played that round's need in the window (run bets, special entries and pot attempts; `MS.NEED` × `MS.STEPS`), and then waits for the player to claim it (`MS.claim`, `POST /api/missions/claim`). Released SOL that isn't claimed stays the player's after its window ends (`ms.ready`), and the server counts it as owed in the cover check. A round pays the window's share of the play its need adds, so a window never pays more than its share of what was played in it, and the shares add up to at most half the house's smallest edge against a good player (1%) across days and weeks together (`MS.RATE`, 0.5%): a good player who plays just enough to collect still loses. Raise a need to raise a reward; don't raise the shares. `node sim/missions.cjs` measures how many runs each round takes and checks that rule; run it after changing a target, a kind or the bot.
- **Duels:** two players fly the same course from one seed and whoever gets further takes the pot: more rings, then the higher score, then a split. The house's only edge is `DU.RAKE` (10%) of each entry; never let it take a side, and never let the demo's autopilot rival stand in for a player on the server. Both flights are judged only from the server's replay of the taps. A player with nobody to race sets the mark (status `waiting`, its entry held and counted as owed); the next player to enter from another wallet races it and gets its taps to draw as a ghost, so the mark's seed stays shut until then. A player past a rival who's out stops there (`stop`), which can never add a ring. A mark nobody takes on is refunded in full after `DUEL_WAIT_MS`. An entry counts as play (missions, rakeback, trophy SOL) only when the duel settles, so parking marks that get refunded earns nothing. The course has to end everyone: keep it in the ring band, getting harder ring by ring (`DU.ringConfig`) with the ball's speed fixed, and check with the bots that even a pro rarely flies all of it.
- **Rakeback:** a share of what was bet, never of what was lost (a share of losses pays for the swings: bet big once, claim on a loss, keep a win). Each bet sets aside `LV.RATE` (20%) of the least the house keeps of it (`LV.CUT`: 1% of a run, 5% of a special entry, 10% of a pot attempt or a settled duel entry), and a level up releases it to claim. Mission SOL, rakeback and trophy SOL together must stay under the house's smallest edge on a run (0.5% + 0.2% + 0.2% against 1%); change `CUT` when an edge changes. Levelling decides only when rakeback can be claimed, so the level curve is free to change; the server releases on its own XP (verified runs and missions).
- **Trophy SOL:** each trophy pays its XP × `TR.UNIT` in SOL (0.001 to 0.025 SOL, 0.085 for all fifteen), claimed with a button on the Trophies page. A player can claim trophy SOL only up to `TR.RATE` (0.2%) of everything they've bet (run bets, special entries, pot attempts and settled duel entries), the smallest rewards first, each trophy once, so it never adds more than that to anyone's return and a fresh account can't farm the easy trophies (it would have to bet 500 times a reward first). Mission SOL, rakeback and trophy SOL together must stay under the house's smallest edge on a run (0.5% + 0.2% + 0.2% against 1%). Raise `UNIT` to pay more per trophy (players then bet more before each claim); don't raise `RATE` past what's left of that edge. Trophies are judged only from a regular run's verified levels (`TR.run` in the server's `settle`), never from the client's word; special levels and practice runs don't count.
- **Before publishing:** `npm run build && SERVER_URL=/ node build.cjs`, `npm test` (server), `python3 tools/flows.py`, `python3 tools/features.py`, `python3 tools/contact.py`, `python3 tools/pot_flow.py`, `python3 tools/ui.py`, `python3 tools/special_flow.py`, `python3 tools/missions_flow.py`, `python3 tools/duel_flow.py`, `python3 tools/server_flow.py`, `python3 tools/desktop.py`, `node sim/missions.cjs 14` and `npm run check`. After camera or spacing changes, `python3 tools/speed.py` reports how much of the next ring is in view deep into a run.
